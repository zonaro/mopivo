# Landing page (`/docs`)

> **Hard rule — no exceptions.**
> **Every major implementation MUST add a section describing it on the landing
> page under `/docs`, written in marketing / conversion language — not technical
> language.**

"Major implementation" = a user-visible feature or capability worth telling a
prospective user about (a new source, a new mode, a new generator preset family,
etc.). It is the same set of issues labeled `major` in
[`issues.md`](issues.md). Small fixes, refactors and internal chores do not need
a section.

## Where the landing page lives

- `docs/index.html` — the page itself. Served by GitHub Pages from `/docs`.
- `docs/i18n.js` — client-side i18n for the landing page (separate from the
  app's gettext; see [`i18n.md`](i18n.md)).
- Icons/assets: `docs/icon-*.png`, regenerated by `scripts/export-icons.sh`.

Live site: <https://zonaro.github.io/mopivo/>.

## Tone rule

**Write for a person deciding whether to install the app, not for a developer.**

- Lead with the benefit and the feeling ("Your desktop comes alive", "each
  monitor gets its own video"), then the feature name.
- No jargon, no API names, no file paths, no `gsettings` keys, no class names.
- Short, punchy sentences. Emojis and bold are welcome here (marketing surface),
  unlike in code.
- End with or near a call to action when it fits (install command, "try it").

> Good: "**Real video wallpapers** — each monitor gets its own video, fit modes,
> volume, mute, Next and Shuffle — plus YouTube links."
> Bad: "The renderer subprocess uses `playbin` + `xvimagesink` under
> `GDK_BACKEND=x11` to set `_NET_WM_WINDOW_TYPE_DESKTOP`."

## How to add a section

1. **Only after the issue exists** and is labeled `major`
   ([`issues.md`](issues.md)).
2. Pick the right place in `docs/index.html`: extend an existing section
   (`#recursos` feature cards, `#provedores` sources, `#como-funciona` install,
   `#faq`) or add a new `<section id="…">` following the existing markup
   pattern (eyebrow → `h2` → `lead` → cards/steps).
3. **Use the existing i18n attributes** — never inline English-only text:
   - `data-i18n="key"` for plain text;
   - `data-i18n-html="key"` when markup must stay (e.g. a `<span class="grad">`);
   - `data-i18n-alt="key"` for image `alt`.
4. **Add the key to every language in `docs/i18n.js`** (en, pt-BR, es). English
   is the fallback; keep translations natural, not literal.
5. Update any counters/claims that change (e.g. the hero says "**8 sources**",
   stats block) so the copy stays truthful.
6. Before finishing: open `docs/index.html` and confirm the new section renders,
   the language switcher shows the new strings, and no key is missing.

## Checklist

- [ ] Issue exists and is labeled `major`.
- [ ] New copy is marketing/conversion language, zero technical terms.
- [ ] Keys added to **all** languages in `docs/i18n.js`.
- [ ] Section follows the existing markup pattern and fits the flow.
- [ ] Counters/claims elsewhere on the page updated if they changed.
- [ ] Rendered page verified.
