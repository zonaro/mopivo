# Internationalization (i18n)

## App (gettext)

- **Domain:** `mopivo` (`TEXT_DOMAIN`), set by `main.js`.
- **Helper:** `lib/i18n.js` provides `initI18n(lang)` (selects the language,
  setting up libc locale + bindtextdomain) and `_(str)` (translates a string).
- **Languages:** English (default/fallback), **pt-BR**, **es**. Auto-detect the
  user's language at runtime, fall back to English.
- **Rule:** all user-facing strings go through `_(…)`. No hardcoded UI text.

### Workflow

1. Wrap new strings with `_()` in the source.
2. Refresh the template: `locale/mopivo.pot`.
3. Update the per-language catalogs under `locale/pt_BR/LC_MESSAGES/` and
   `locale/es/LC_MESSAGES/`.
4. Compile in-tree with `make i18n` (writes the `.mo` files; these are
   gitignored). The installer compiles them to
   `~/.local/share/locale/<lang>/LC_MESSAGES/mopivo.mo`.
5. `make check` does not validate translations — verify manually that new keys
   appear in every catalog.

Keep translations natural and contextual, not literal. When a string embeds
markup, keep the tags intact across languages.

## Landing page (separate, client-side)

The landing page in `/docs` has its **own** i18n, unrelated to gettext:

- `docs/i18n.js` holds the dictionaries for en / pt-BR / es.
- Strings are referenced from `docs/index.html` via:
  - `data-i18n="key"` — plain text,
  - `data-i18n-html="key"` — markup that must be preserved,
  - `data-i18n-alt="key"` — image `alt` text,
  - a `meta.*` group for meta tags.
- **Every new key must be added to all three languages.** English is the
  fallback.

Whenever you touch the landing page (see [`landing.md`](landing.md)), keep the
three dictionaries in sync and verify the language switcher renders the new
strings.
